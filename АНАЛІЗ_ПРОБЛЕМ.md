# Аналіз проблем та недоліків проекту

## 🔴 КРИТИЧНІ ПРОБЛЕМИ

### 1. Відсутність централізованої валідації
**Проблема:** `express-validator` та `joi` встановлені в `package.json`, але НЕ використовуються. Валідація робиться вручну в кожному контролері.

**Приклад проблеми:**
```typescript
// backend/src/controllers/auth.controller.ts:15
const { email, password, firstName, lastName, role, requestedCourseId } = req.body;
// Немає перевірки формату email, мінімальної довжини пароля, тощо
```

**Ризики:**
- SQL injection через невалідовані дані
- XSS атаки через неочищені рядки
- Некоректні дані в базі даних
- Проблеми з безпекою

**Рішення:** Створити middleware для валідації з використанням `express-validator`.

---

### 2. Використання `any` типів
**Проблема:** TypeScript `any` використовується в критичних місцях, що знижує типобезпеку.

**Місця:**
- `backend/src/utils/dbErrorHandler.ts:37` - `error: any`
- `frontend/src/pages/admin/AnalyticsPage.tsx:70-75` - `(u: any)`, `(c: any)`, `(e: any)`
- `frontend/src/pages/dashboard/DashboardPage.tsx:80` - `error: any`

**Ризики:**
- Помилки під час виконання через неправильні типи
- Втрата переваг TypeScript
- Складність підтримки коду

**Рішення:** Замінити всі `any` на конкретні типи або `unknown` з type guards.

---

### 3. Використання `console.log/error` замість logger
**Проблема:** У frontend використовується `console.log` та `console.error` замість налаштованого logger.

**Місця (51 випадок):**
- `frontend/src/pages/dashboard/DashboardPage.tsx:78,81`
- `frontend/src/pages/admin/AnalyticsPage.tsx:103`
- `frontend/src/pages/courses/CoursesPage.tsx:58,100`
- І ще 48 місць...

**Ризики:**
- Логи в production режимі
- Неможливість контролю рівня логування
- Проблеми з дебагом

**Рішення:** Замінити всі `console.*` на `logger.*` з `frontend/src/utils/logger.ts`.

---

## 🟡 СЕРЙОЗНІ ПРОБЛЕМИ

### 4. Відсутність sanitization вхідних даних
**Проблема:** Немає очищення вхідних даних від потенційно небезпечного контенту.

**Приклад:**
```typescript
// backend/src/controllers/course.controller.ts:186
const { title, slug, description, ... } = req.body;
// Дані безпосередньо передаються в Prisma без очищення
```

**Ризики:**
- XSS атаки через неочищені рядки
- Проблеми з відображенням HTML/JS в UI
- Потенційні проблеми з безпекою

**Рішення:** Додати sanitization middleware (наприклад, `dompurify` для frontend, `sanitize-html` для backend).

---

### 5. Непослідовна обробка помилок
**Проблема:** Деякі контролери використовують `return next(error)`, інші просто `next(error)`.

**Приклади:**
- `backend/src/controllers/assignment.controller.ts:95` - `return next(error)`
- `backend/src/controllers/course.controller.ts:171` - `next(error)` (без return)

**Ризики:**
- Можливі подвійні відповіді
- Непередбачувана поведінка

**Рішення:** Стандартизувати обробку помилок - завжди використовувати `return next(error)`.

---

### 6. Потенційні N+1 запити
**Проблема:** Деякі запити можуть викликати N+1 проблему через відсутність `include`.

**Приклад:**
```typescript
// Можлива проблема в enrollment.controller.ts
const enrollments = await prisma.enrollment.findMany({
  where: { courseId },
  include: { user: { select: {...} } }
});
// Якщо потім робиться додатковий запит для кожного enrollment
```

**Ризики:**
- Повільна робота при великій кількості даних
- Навантаження на базу даних

**Рішення:** Перевірити всі контролери на N+1 проблеми та додати необхідні `include`.

---

### 7. Відсутність валідації email формату
**Проблема:** Email не перевіряється на коректність формату перед збереженням.

**Приклад:**
```typescript
// backend/src/controllers/auth.controller.ts:15
const { email, password, ... } = req.body;
// Перевіряється тільки чи email існує, але не формат
```

**Ризики:**
- Некоректні дані в базі
- Проблеми з відправкою email

**Рішення:** Додати валідацію email через regex або бібліотеку.

---

### 8. Помилка в логуванні
**Проблема:** У `createCourse` логується помилка з неправильним повідомленням.

**Приклад:**
```typescript
// backend/src/controllers/course.controller.ts:241
logger.error('Error in getCourses:', error);
// Але це функція createCourse, не getCourses!
```

**Рішення:** Виправити повідомлення на `'Error in createCourse:'`.

---

## 🟢 ДРІБНІ ПРОБЛЕМИ ТА ПОКРАЩЕННЯ

### 9. Відсутність обмежень на деякі endpoints
**Проблема:** Rate limiting застосований тільки до `/api/auth` та загальний `/api`, але деякі важкі endpoints можуть потребувати окремих обмежень.

**Рішення:** Додати окремі rate limiters для:
- `/api/courses` (може бути важким при великій кількості курсів)
- `/api/submissions` (може бути важким при перевірці)

---

### 10. Непослідовність у обробці файлів
**Проблема:** У `file.routes.ts` використовується `upload.array('files', 10)`, але в `upload.ts` обмеження `files: 5`.

**Рішення:** Узгодити обмеження - або 5, або 10 файлів.

---

### 11. Відсутність перевірки MIME типів файлів
**Проблема:** Перевіряється тільки розширення файлу, але не MIME тип.

**Ризики:**
- Можливість завантаження небезпечних файлів з підробленим розширенням

**Рішення:** Додати перевірку MIME типів у `fileFilter`.

---

### 12. Відсутність валідації паролів
**Проблема:** Паролі не перевіряються на мінімальну довжину, складність тощо.

**Ризики:**
- Слабкі паролі
- Проблеми з безпекою

**Рішення:** Додати валідацію паролів (мінімум 8 символів, великі/малі літери, цифри).

---

### 13. Використання `req.user!` без перевірки
**Проблема:** У деяких місцях використовується `req.user!` після перевірки, але TypeScript не розуміє це.

**Приклад:**
```typescript
// backend/src/controllers/submission.controller.ts:61
userId: req.user!.id,
// Після перевірки if (!req.user), але TypeScript не знає про це
```

**Рішення:** Використовувати type guard або явну перевірку перед використанням.

---

### 14. Відсутність індексування в базі даних
**Проблема:** Деякі часто використовувані поля можуть потребувати індексів для швидкості.

**Рішення:** Перевірити схему Prisma та додати індекси для:
- `User.email` (вже є `@unique`)
- `Course.slug` (вже є `@unique`)
- `Enrollment.userId_courseId` (вже є `@@unique`)

---
